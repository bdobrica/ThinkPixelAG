# ThinkPixelAG 0.1.0-rc.1 — integration candidate

Proposed semantic version: **0.1.0-rc.1**; proposed Git tag: **v0.1.0-rc.1**.
This document does not create a tag or publish a formal release. Exact source
and final artifact digests are recorded in [final artifact qualification](final-artifacts.md).

## Scope

This candidate provides AG's governance component for integration development:
verified identity and policy, immutable agent/version authority, governed Run
admission/lifecycle, transactional resource accounting, ordered revocation and
freshness, privileged approval/signing boundaries and durable governance evidence.
It includes restricted OCI/Kubernetes packaging and operational qualification.

OpenAPI is frozen at `0.1.0-rc.1`; the existing policy wire identifier remains
`thinkpixelag.authorization/v1alpha1`. The [compatibility review](../../contracts/compatibility.md)
found no request/response/schema change from Phase 8 beyond status metadata.
Database schema remains 18; Phase 9 introduces no migration.

Operational fixes included in the candidate make admission/replay response
atomic, preserve current approval checks under concurrency, and preserve pending
evidence identity across uncertain delivery and lease takeover. Optional Valkey
throughput hints now compose into trusted usage without becoming authoritative.

## Known limitations

- This is an integration candidate, not production-capacity or whole-platform
  qualification. [DQ-001–004](../../adr/0012-integration-rc-qualification-deferrals.md) retain
  throughput/drops/tail latency, full workload/fanout/backlog, AR/gateway and
  intended-production HA qualification. Production SLOs remain unchanged.
- The [measured homelab point](../../operations/capacity.md) is 25 admissions/s for five
  minutes with durable evidence and no drops; separate read tests do not create
  a combined workload guarantee. The SSD database/sink share one failure domain.
- AG does not execute Codex or another harness and has no versioned AR worker
  API yet. Registry/policy-management services are not composed into the current
  executable's runtime routes. Integrators need pre-provisioned approved fixtures
  and the documented runtime/OIDC/mTLS configuration.
- Production KMS/HSM/IdP ceremonies remain unqualified; component tests and
  [game-day scope](game-days.md) do not claim a selected provider deployment.
- The [risk record](risk-review.md) preserves medium/unknown dependency findings
  and exact dependency-policy exceptions. Refresh scans before distribution.
- The current executable uses live policy/revocation checks; its optional Valkey
  wiring accelerates throughput hints, not cached authorization decisions.

## Installation and upgrade notes

Follow [runtime configuration](../../operations/configuration.md#governed-runtime-composition),
[deployment guidance](../../../deploy/README.md) and [runbooks](../../operations/runbooks.md).
Use the immutable final digest and an environment overlay with explicit secret
delivery and allowed dependency destinations. The base manifest is a template.
Run the migration Job before admitting traffic; do not migrate from API startup.

There is no prior tagged release to upgrade from. Existing schema-18 homelab
state needs no Phase 9 migration. For earlier fixtures, rehearse forward migration
and backup recovery; migration 016 rejects legacy policy validation and requires
re-promotion through the signed envelope. Preserve the approved policy, workload
bindings, cursor secrets, outbox/checkpoints and authoritative database state.
Rotate cursor secrets only with the expected invalidation/reconciliation plan.

Rollback means selecting a compatible prior image and following the tested
procedure, not automatically down-migrating the schema. Never restart retained
stale database or evidence-sink writers behind authoritative Services. After
rollout, check readiness, governed admission/replay/denial, epochs, allocations
and evidence drain/chain continuity. Keep all retained test resources until
the operator requests removal.

## Verification and artifact inventory

See [clean-checkout/fuzz/live smoke](verification.md), [risk gate](risk-review.md),
[game days](game-days.md) and [traceability](reconciliation.md).

The release bundle consists of:

| Artifact | Identity / purpose |
|---|---|
| Multiarchitecture OCI index and explicit AMD64/ARM64 manifests | Immutable digests; source/version/creation/license labels; BuildKit SBOM/provenance attachments |
| Per-platform CycloneDX SBOM and vulnerability JSON | Scan the explicit platform manifest; reject HIGH/CRITICAL including unfixed findings |
| OpenAPI, four versioned JSON Schemas and Kubernetes archive | Generated/copied from the same clean source commit; archive timestamps use that commit |
| `provenance.json` | `thinkpixelag.release-artifacts/v1` unsigned local inventory: actual OCI SHA-256, source commit, version and source timestamp; not SLSA or proof of builder identity |
| `SHA256SUMS` | Validate each platform bundle; CI additionally checksums the two platform archives |
| Optional cosign verification and GitHub attestation | Separate authenticated outputs only when executed; their availability must be stated explicitly |

The artifact helper now rejects mutable image tags, mismatched source commit or
timestamp, and dirty/untracked source. It does not independently prove that a
remote image was built from the supplied commit: RC-012 verifies build metadata,
manifest/config labels and attachment relationships as a separate step.
Historical Phase 8 artifacts retain their old metadata; they are not silently
renamed to this version. The final inventory must state signing/tag/publication
status rather than infer it from the presence of JSON files.

## Operator acceptance checklist

- Select the intended identity/provider/dependency overlay and verify its trust
  and network boundaries; keep production qualification separate from this RC.
- Verify source commit, immutable index/platform digests, checksum inventories,
  SBOM/scans and any actually available signature/attestation identities.
- Back up authoritative state, confirm the migration/rollback plan and fence
  old writers before switching storage endpoints.
- Configure runtime routes, OIDC, approved policy/agent fixtures and cursor keys;
  configure the separate mTLS listener for trusted APIs.
- Confirm readiness and governed replay/denial behavior; observe resource
  invariants, revocation freshness and durable evidence delivery while increasing
  traffic within the measured envelope.
- Record deployment-specific provider/AR/gateway/HA qualification before making
  the corresponding production claim.
